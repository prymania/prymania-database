🎯 เมื่อเรียนจบบทนี้ นิสิตจะสามารถ
  1. อธิบายหลักการทำงานของดัชนี และความแตกต่างระหว่าง Full Table Scan กับการค้นผ่านดัชนีได้
  2. อ่านผล EXPLAIN เพื่อตรวจว่าคำสั่งใช้ดัชนีหรือไม่ได้
  3. สร้าง ตรวจสอบ และลบดัชนีได้ รวมถึงดัชนีหลายคอลัมน์และดัชนี UNIQUE
  4. อธิบายกฎ Leftmost Prefix และกรณีที่ดัชนีใช้ไม่ได้
  5. เลือกคอลัมน์ที่ควรสร้างดัชนีได้อย่างมีเหตุผล โดยคำนึงถึงต้นทุน

8.1 แนวคิดของดัชนี

ดัชนี (Index) คือโครงสร้างข้อมูลเสริมที่ DBMS สร้างขึ้นจากค่าของคอลัมน์ที่เลือก เพื่อให้หาแถวที่ต้องการได้โดยไม่ต้องอ่านทุกแถว — เหมือนดัชนีท้ายเล่มหนังสือที่บอกว่าคำนี้อยู่หน้าไหน

ไม่มีดัชนี — Full Table Scan

หา stdid = '60010' ต้องอ่านทีละแถวตั้งแต่แถวแรกจนแถวสุดท้าย — ตาราง 1 ล้านแถว ต้องตรวจ 1 ล้านแถว เวลาที่ใช้เพิ่มตามจำนวนแถว

มีดัชนี — Index Lookup

ดัชนีเรียงค่าไว้แล้วในโครงสร้างต้นไม้ ไล่จากราก → กิ่ง → ใบ ไม่กี่ขั้นก็เจอ — ตาราง 1 ล้านแถว ใช้ราว 3–4 ขั้น เวลาเพิ่มตามลอการิทึมของจำนวนแถว

โครงสร้าง B-Tree (แบบย่อ)

MySQL (InnoDB) เก็บดัชนีเป็น B+Tree — โหนดบนสุดเป็นตัวแบ่งช่วง โหนดใบเก็บค่าที่เรียงแล้วพร้อมตัวชี้ไปยังแถวจริง

ดัชนีบนคอลัมน์ major (แนวคิด)
                       [ English | Physics ]                  ← ราก (root)
                 /               |               \
      [ Art | CS ]        [ English | Math ]       [ Physics ]   ← กิ่ง
        |      |              |        |               |
   Art→60007  CS→60001    English→60009 Math→60005  Physics→60014  ← ใบ (leaf)
   Art→60008  CS→60002    English→60010 Math→60006  Physics→60015     เรียงตามค่า
              CS→60003    ...                       Physics→60016     + ตัวชี้ไปยังแถว
              ...

ค้นหา major = 'Math': เริ่มที่ราก → 'Math' อยู่ระหว่าง English กับ Physics → ไปกิ่งกลาง → ไปใบ Math → ได้ตัวชี้ไปยังแถวของ 60005, 60006 ทันที

💡 ดัชนีที่มีอยู่แล้วโดยอัตโนมัติ

MySQL สร้างดัชนีให้เองกับ PRIMARY KEY, UNIQUE และ FOREIGN KEY — ตารางในกรณีศึกษาจึงมีดัชนีอยู่แล้วหลายตัว

SHOW INDEX FROM enroll;

enroll มีดัชนี PRIMARY (secid, stdid) และ enroll_fk_std (stdid) ที่ MySQL สร้างให้สำหรับคีย์นอก

8.2 อ่านแผนการทำงานด้วย EXPLAIN

เติม EXPLAIN หน้า SELECT เพื่อดูว่า DBMS วางแผนจะหาข้อมูลอย่างไร (ไม่ได้รันคำสั่งจริง)

EXPLAIN SELECT * FROM student WHERE stdid = '60010'; EXPLAIN SELECT * FROM student WHERE name = 'Gon';
คอลัมน์ความหมาย
typeวิธีเข้าถึงข้อมูล (ดูตารางถัดไป) — สำคัญที่สุด
possible_keysดัชนีที่ใช้ได้
keyดัชนีที่เลือกใช้จริง (NULL = ไม่ใช้ดัชนี)
rowsจำนวนแถวที่คาดว่าต้องตรวจ — ยิ่งน้อยยิ่งดี
filteredร้อยละของแถวที่คาดว่าผ่านเงื่อนไข
Extraข้อมูลเพิ่ม เช่น Using where, Using index, Using filesort
type (ดี → แย่)ความหมาย
constหาด้วย PK/UNIQUE ได้แถวเดียว — เร็วที่สุด
eq_refJOIN ด้วย PK/UNIQUE ทีละแถว
refหาด้วยดัชนีที่ไม่ unique ได้หลายแถว
rangeหาช่วงค่าด้วยดัชนี เช่น BETWEEN, >, <, LIKE 'S%'
indexอ่านดัชนีทั้งหมด (ดีกว่า ALL เล็กน้อย)
ALLFull Table Scan — อ่านทุกแถว

รัน EXPLAIN SELECT * FROM enroll WHERE stdid = '60001'; แล้วตอบว่าใช้ดัชนีใด type อะไร และทำไมใช้ดัชนีได้ทั้งที่เราไม่เคยสร้างดัชนีเอง

EXPLAIN SELECT * FROM enroll WHERE stdid = '60001';

ใช้ดัชนี enroll_fk_std (type = ref) ซึ่ง MySQL สร้างให้อัตโนมัติเพราะ stdid เป็นคีย์นอก

8.3 การสร้าง ตรวจสอบ และลบดัชนี

รูปแบบคำสั่ง
-- สร้างดัชนี
CREATE [UNIQUE] INDEX ชื่อดัชนี ON ชื่อตาราง (คอลัมน์1 [, คอลัมน์2, ...]);
ALTER TABLE ชื่อตาราง ADD INDEX ชื่อดัชนี (คอลัมน์);

-- สร้างพร้อมตาราง
CREATE TABLE t ( ..., INDEX idx_name (คอลัมน์) );

-- ดู / ลบ
SHOW INDEX FROM ชื่อตาราง;
DROP INDEX ชื่อดัชนี ON ชื่อตาราง;

ตั้งชื่อด้วย idx_ตาราง_คอลัมน์ (หรือ uidx_ สำหรับ UNIQUE) จะรู้ทันทีว่าดัชนีนี้ใช้กับอะไร

EXPLAIN SELECT stdid, name FROM student WHERE major = 'CS'; CREATE INDEX idx_student_major ON student(major); EXPLAIN SELECT stdid, name FROM student WHERE major = 'CS'; SHOW INDEX FROM student; DROP INDEX idx_student_major ON student;
📝 ตารางเล็กมาก

student มีแค่ 22 แถว แม้มีดัชนี DBMS บางครั้งก็เลือกอ่านทั้งตาราง เพราะเร็วกว่าการไล่ดัชนี — ผลต่างของดัชนีจะเห็นชัดเมื่อข้อมูลมาก (หัวข้อถัดไป)

8.4 ทดลองกับข้อมูลขนาดใหญ่

สร้างตาราง enroll_log ขนาด 50,000 แถวด้วย Recursive CTE เพื่อเห็นผลของดัชนีชัดเจน

CREATE TABLE enroll_log ( log_id INT AUTO_INCREMENT PRIMARY KEY, stdid VARCHAR(10), secid INT, grade CHAR(1), log_date DATE ); SET SESSION cte_max_recursion_depth = 100000; INSERT INTO enroll_log (stdid, secid, grade, log_date) WITH RECURSIVE n AS (SELECT 1 AS i UNION ALL SELECT i + 1 FROM n WHERE i < 50000) SELECT CONCAT('6', LPAD(MOD(i * 37, 5000), 4, '0')), MOD(i, 52) + 1, ELT(MOD(i, 5) + 1, 'A', 'B', 'C', 'D', 'F'), DATE_ADD('2023-01-01', INTERVAL MOD(i, 1200) DAY) FROM n; ANALYZE TABLE enroll_log; SELECT COUNT(*) AS n_rows, COUNT(DISTINCT stdid) AS n_student FROM enroll_log; EXPLAIN SELECT * FROM enroll_log WHERE stdid = '61234'; CREATE INDEX idx_log_stdid ON enroll_log(stdid); EXPLAIN SELECT * FROM enroll_log WHERE stdid = '61234';

จำนวนแถวที่ต้องตรวจ (rows) ลดจากราว 50,000 เหลือไม่กี่แถว — ยิ่งตารางใหญ่ ความต่างยิ่งมาก

EXPLAIN SELECT COUNT(*) FROM enroll_log WHERE log_date BETWEEN '2024-03-01' AND '2024-03-07'; CREATE INDEX idx_log_date ON enroll_log(log_date); EXPLAIN SELECT COUNT(*) FROM enroll_log WHERE log_date BETWEEN '2024-03-01' AND '2024-03-07';

จงตรวจด้วย EXPLAIN ว่า SELECT * FROM enroll_log WHERE secid = 10 ใช้ดัชนีหรือไม่ แล้วสร้างดัชนีให้เหมาะสมและตรวจอีกครั้ง

EXPLAIN SELECT * FROM enroll_log WHERE secid = 10; CREATE INDEX idx_log_secid ON enroll_log(secid); EXPLAIN SELECT * FROM enroll_log WHERE secid = 10;

rows ลดลงจากราว 50,000 เหลือราว 1,000 (ทุก 52 แถวมี secid เดียวกัน 1 แถว)

8.5 ดัชนีหลายคอลัมน์ และกฎ Leftmost Prefix

ดัชนีหลายคอลัมน์ (a, b) เรียงตาม a ก่อน แล้วจึงเรียงตาม b ภายใน a เดียวกัน — เหมือนสมุดโทรศัพท์ที่เรียงตามนามสกุลก่อน แล้วจึงชื่อ

💡 Leftmost Prefix

ดัชนี (a, b, c) ใช้ได้กับเงื่อนไขบน a, (a, b), (a, b, c) — แต่ใช้ไม่ได้กับเงื่อนไขบน b หรือ c อย่างเดียว (เปิดสมุดโทรศัพท์หาคนชื่อ “สมชาย” โดยไม่รู้นามสกุล ต้องอ่านทั้งเล่ม)

CREATE INDEX idx_log_grade_date ON enroll_log(grade, log_date); EXPLAIN SELECT COUNT(*) FROM enroll_log WHERE grade = 'F' AND log_date BETWEEN '2024-01-01' AND '2024-01-31'; EXPLAIN SELECT COUNT(*) FROM enroll_log WHERE grade = 'F'; DROP INDEX idx_log_date ON enroll_log; EXPLAIN SELECT COUNT(*) FROM enroll_log WHERE log_date BETWEEN '2024-01-01' AND '2024-01-31';
📝 สังเกต type = index

บางครั้ง MySQL เลือก “อ่านดัชนีทั้งหมด” (type = index) แทนการอ่านตาราง เพราะดัชนีเล็กกว่า — แต่ก็ยังต้องอ่านทุกรายการ (rows ≈ 50,000) ไม่ได้ใช้ประโยชน์จากการเรียงลำดับ

ถ้าคำสั่งที่ใช้บ่อยคือ (1) WHERE secid = ? (2) WHERE secid = ? AND grade = ? (3) WHERE grade = ? (นาน ๆ ครั้ง) ควรสร้างดัชนี (secid, grade) หรือ (grade, secid) เพราะเหตุใด

ควรเลือก (secid, grade) — ใช้ได้กับคำสั่ง (1) และ (2) ซึ่งใช้บ่อย ตามกฎ Leftmost Prefix ส่วน (3) นาน ๆ ครั้งยอมให้ช้าได้ หรือถ้าสำคัญจริงก็สร้างดัชนีแยกบน grade (แต่ grade มีแค่ 5 ค่า ประโยชน์น้อย)

8.6 Covering Index

ถ้าทุกคอลัมน์ที่คำสั่งต้องใช้ (ทั้งใน SELECT และ WHERE) อยู่ในดัชนีครบ DBMS ตอบจากดัชนีได้เลยโดยไม่ต้องไปอ่านแถวจริง — EXPLAIN จะแสดง Extra = Using index

CREATE INDEX idx_log_cover ON enroll_log(grade, log_date, stdid); EXPLAIN SELECT stdid FROM enroll_log WHERE grade = 'F' AND log_date BETWEEN '2024-01-01' AND '2024-01-31'; EXPLAIN SELECT * FROM enroll_log WHERE grade = 'F' AND log_date BETWEEN '2024-01-01' AND '2024-01-31';

นี่คืออีกเหตุผลที่ไม่ควรใช้ SELECT * ในโปรแกรมจริง

8.7 กรณีที่ดัชนีใช้ไม่ได้

กรณีตัวอย่างที่ใช้ดัชนีไม่ได้เขียนใหม่ให้ใช้ดัชนีได้
ใช้ฟังก์ชันกับคอลัมน์WHERE YEAR(log_date) = 2024WHERE log_date BETWEEN '2024-01-01' AND '2024-12-31'
LIKE ขึ้นต้นด้วย %WHERE stdid LIKE '%234'WHERE stdid LIKE '61%' (ถ้าโจทย์อนุญาต)
ชนิดข้อมูลไม่ตรงWHERE stdid = 61234 (ตัวเลข เทียบกับ VARCHAR)WHERE stdid = '61234'
คำนวณกับคอลัมน์WHERE secid + 1 = 11WHERE secid = 10
ข้ามคอลัมน์ซ้ายสุดดัชนี (grade, log_date) กับ WHERE log_date = …สร้างดัชนีที่ขึ้นต้นด้วย log_date
CREATE INDEX idx_log_date ON enroll_log(log_date); EXPLAIN SELECT COUNT(*) FROM enroll_log WHERE YEAR(log_date) = 2024; EXPLAIN SELECT COUNT(*) FROM enroll_log WHERE log_date BETWEEN '2024-01-01' AND '2024-12-31'; EXPLAIN SELECT * FROM enroll_log WHERE stdid = 61234; EXPLAIN SELECT * FROM enroll_log WHERE stdid = '61234'; EXPLAIN SELECT * FROM enroll_log WHERE stdid LIKE '%234';

คำสั่ง SELECT * FROM enroll_log WHERE MONTH(log_date) = 3 AND YEAR(log_date) = 2025; ใช้ดัชนี idx_log_date ไม่ได้ จงเขียนใหม่ให้ใช้ได้ แล้วตรวจด้วย EXPLAIN

EXPLAIN SELECT * FROM enroll_log WHERE log_date >= '2025-03-01' AND log_date < '2025-04-01';

ใช้ < '2025-04-01' แทน <= '2025-03-31' จะปลอดภัยกว่าเมื่อคอลัมน์เป็น DATETIME (มีเวลาด้วย)

8.8 ดัชนี UNIQUE และดัชนีกับการเรียงลำดับ

UNIQUE INDEX ทำหน้าที่ทั้งเร่งการค้นหาและบังคับไม่ให้ค่าซ้ำ (เหมือนข้อกำหนด UNIQUE)

CREATE UNIQUE INDEX uidx_subject_name ON subject(name); INSERT INTO subject (subid, name, credit, major) VALUES ('CS011', 'Database', 3, 'CS'); CREATE UNIQUE INDEX uidx_student_name ON student(name);

ดัชนีช่วย ORDER BY ได้ด้วย เพราะข้อมูลในดัชนีเรียงอยู่แล้ว — ถ้าไม่มี MySQL ต้องเรียงเอง (Using filesort)

EXPLAIN SELECT * FROM enroll_log ORDER BY log_date LIMIT 10; EXPLAIN SELECT * FROM enroll_log ORDER BY secid DESC, stdid LIMIT 10;

8.9 ต้นทุนของดัชนี และแนวทางการเลือก

ดัชนีไม่ใช่ของฟรี — ทุกครั้งที่ INSERT / UPDATE / DELETE DBMS ต้องปรับดัชนีทุกตัวที่เกี่ยวข้อง และดัชนีใช้เนื้อที่ดิสก์เพิ่ม

SELECT TABLE_NAME, ROUND(DATA_LENGTH / 1024) AS data_kb, ROUND(INDEX_LENGTH / 1024) AS index_kb FROM information_schema.TABLES WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'enroll_log';

✅ ควรสร้างดัชนีเมื่อ

  • ใช้ใน WHERE บ่อย และค่ามีความหลากหลายสูง
  • ใช้เป็นเงื่อนไข JOIN (FK มีให้อัตโนมัติ)
  • ใช้ใน ORDER BY / GROUP BY บ่อย
  • ต้องบังคับไม่ให้ซ้ำ (UNIQUE)
  • ตารางใหญ่และอ่านบ่อยกว่าเขียน

❌ ไม่ควรสร้างเมื่อ

  • ตารางเล็กมาก (อ่านทั้งตารางเร็วกว่า)
  • ค่าซ้ำกันมาก เช่น เพศ, grade
  • ตารางถูกเพิ่ม/แก้ถี่มาก เช่น log
  • คอลัมน์แทบไม่เคยใช้ในเงื่อนไข
  • มีดัชนีที่ขึ้นต้นด้วยคอลัมน์เดียวกันอยู่แล้ว
✅ ขั้นตอนการปรับประสิทธิภาพ
  1. หาคำสั่งที่ช้า / ใช้บ่อย
  2. EXPLAIN ดูว่า type = ALL หรือ rows มากหรือไม่
  3. สร้างดัชนีที่ตรงกับ WHERE / JOIN / ORDER BY ของคำสั่งนั้น
  4. EXPLAIN อีกครั้งเพื่อยืนยัน
  5. ลบดัชนีที่ไม่มีใครใช้

ตาราง enroll_log มีดัชนี idx_log_grade_date (grade, log_date) และ idx_log_cover (grade, log_date, stdid) — ดัชนีใดซ้ำซ้อน ควรลบตัวใด เพราะเหตุใด

idx_log_grade_date ซ้ำซ้อน เพราะ idx_log_cover ขึ้นต้นด้วย (grade, log_date) เหมือนกัน ใช้แทนได้ทุกกรณี (Leftmost Prefix) — ลบ idx_log_grade_date เพื่อลดต้นทุนการเขียนและเนื้อที่

DROP INDEX idx_log_grade_date ON enroll_log; SELECT DISTINCT INDEX_NAME FROM information_schema.STATISTICS WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'enroll_log';
  • แนวคิดและ EXPLAIN
  • จงอธิบายแนวคิดของดัชนี เปรียบเทียบกับดัชนีท้ายเล่มหนังสือ (B-Tree)

    ดัชนีท้ายเล่มเรียงคำตามตัวอักษรพร้อมเลขหน้า ทำให้หาคำได้ทันทีโดยไม่ต้องอ่านทุกหน้า — ดัชนีของฐานข้อมูลก็เช่นกัน DBMS เก็บค่าของคอลัมน์ที่เลือกเรียงลำดับไว้ในโครงสร้าง B-Tree พร้อมตัวชี้ไปยังแถวจริง การค้นหาจึงไล่จากรากลงไปไม่กี่ชั้น (เวลา ~log n) แทนการอ่านทุกแถว (Full Table Scan) แลกกับพื้นที่เพิ่มและต้องปรับดัชนีทุกครั้งที่ข้อมูลเปลี่ยน

  • ใช้ EXPLAIN ตรวจคำสั่ง SELECT * FROM student WHERE name = 'Rukawa' แล้วอธิบายค่าในคอลัมน์ type, key, rows (type = ALL)
    EXPLAIN SELECT * FROM student WHERE name = 'Rukawa';

    type = ALL คืออ่านทุกแถวของตาราง (Full Table Scan) · key = NULL คือไม่ได้ใช้ดัชนีใด เพราะคอลัมน์ name ยังไม่มีดัชนี · rows คือจำนวนแถวที่ MySQL ประมาณว่าต้องอ่าน (เกือบทั้งตาราง)

  • สร้างและใช้ดัชนี
  • สร้างดัชนีให้คอลัมน์ section.term แล้วเปรียบเทียบผล EXPLAIN ก่อนและหลัง (type: ALL → ref)
    EXPLAIN SELECT * FROM section WHERE term = '2024-1';CREATE INDEX idx_section_term ON section(term); EXPLAIN SELECT * FROM section WHERE term = '2024-1';

    ก่อนสร้าง type = index — MySQL อ่านดัชนี sec_uk ทั้งหมด (term เป็นคอลัมน์ที่ 3 ของ sec_uk จึงค้นตรง ๆ ไม่ได้ ต้องไล่ทุกค่า) rows ≈ ทั้งตาราง หลังสร้าง type = ref key = idx_section_term และ rows ลดเหลือเฉพาะแถวของเทอมนั้น

  • สร้างดัชนีให้ student.name แล้วตรวจว่าคำสั่ง WHERE name LIKE 'Ru%' และ WHERE name LIKE '%wa' ใช้ดัชนีหรือไม่ (wildcard นำหน้า)
    CREATE INDEX idx_student_name ON student(name); EXPLAIN SELECT * FROM student WHERE name LIKE 'Ru%';EXPLAIN SELECT * FROM student WHERE name LIKE '%wa';

    'Ru%' ใช้ดัชนีได้ (type = range) เพราะรู้ตัวอักษรต้น จึงกระโดดไปยังช่วงที่ขึ้นต้นด้วย Ru ในดัชนีที่เรียงไว้ได้ ส่วน '%wa' ใช้ไม่ได้ (type = ALL) เพราะไม่รู้ว่าขึ้นต้นด้วยอะไร ต้องตรวจทุกแถว — เหมือนหาคำที่ “ลงท้ายด้วย wa” ในพจนานุกรม

  • ดัชนี idx(term, lecid) จะช่วยคำสั่ง WHERE lecid = 't01' อย่างเดียวได้หรือไม่ เพราะเหตุใด (Leftmost prefix)

    ไม่ได้ — ดัชนีหลายคอลัมน์เรียงตาม term ก่อน แล้วจึงเรียง lecid ภายในแต่ละ term (เหมือนสมุดโทรศัพท์ที่เรียงนามสกุลก่อนชื่อ) จะใช้ได้ต้องมีเงื่อนไขของคอลัมน์ซ้ายสุด (term) — กฎ Leftmost Prefix

    CREATE INDEX idx_sec_term_lec ON section(term, lecid); EXPLAIN SELECT * FROM section WHERE lecid = 't01';

    สังเกตว่า idx_sec_term_lec ไม่อยู่ใน possible_keys — MySQL ใช้ดัชนี sec_fk_lec ที่สร้างขึ้นอัตโนมัติพร้อม FK ของ lecid แทน

  • ออกแบบดัชนีที่ทำให้คำสั่ง SELECT name FROM lecturer WHERE major = 'English' เป็น Covering Index (Using index)

    สร้างดัชนี (major, name) — major ใช้ค้น และ name เป็นคอลัมน์เดียวที่ต้องแสดง เมื่อทุกคอลัมน์ที่ต้องใช้อยู่ในดัชนีแล้ว MySQL ตอบได้จากดัชนีโดยไม่ต้องอ่านแถวจริง (Extra = Using index)

    CREATE INDEX idx_lec_major_name ON lecturer(major, name); EXPLAIN SELECT name FROM lecturer WHERE major = 'English';EXPLAIN SELECT name, salary FROM lecturer WHERE major = 'English';

    ไม่ได้ — ดัชนีเก็บค่า birthday ไม่ใช่ YEAR(birthday) เมื่อครอบคอลัมน์ด้วยฟังก์ชัน MySQL ต้องคำนวณทุกแถว ต้องเขียนเงื่อนไขเป็นช่วงของคอลัมน์ตรง ๆ แทน

    CREATE INDEX idx_student_bday ON student(birthday); EXPLAIN SELECT * FROM student WHERE YEAR(birthday) = 2010;EXPLAIN SELECT * FROM student WHERE birthday BETWEEN '2010-01-01' AND '2010-12-31';
