🎯 เมื่อเรียนจบบทนี้ นิสิตจะสามารถ
  1. อธิบายแนวคิดของทรานแซกชันและคุณสมบัติ ACID ได้
  2. ควบคุมทรานแซกชันด้วย START TRANSACTION, COMMIT, ROLLBACK และ SAVEPOINT ได้
  3. อธิบายผลของ autocommit และ Implicit Commit ได้
  4. อธิบายปัญหาที่เกิดจากการทำงานพร้อมกัน และเลือกระดับการแยกรายการได้เหมาะสม
  5. ใช้ SELECT … FOR UPDATE เพื่อป้องกัน Lost Update และอธิบาย Deadlock ได้

9.1 แนวคิดของทรานแซกชัน

ทรานแซกชัน (Transaction) คือกลุ่มคำสั่งที่ต้องทำงานเป็นหน่วยเดียว — สำเร็จทั้งหมด หรือไม่สำเร็จเลย

🏦 โอนเงิน 1,000 บาท

  1. หักเงินบัญชี A 1,000
  2. เพิ่มเงินบัญชี B 1,000

ถ้าระบบล่มหลังข้อ 1 → เงินหายไป 1,000 บาท

🎓 ย้ายกลุ่มเรียน

  1. ลบนิสิตออกจาก section 51
  2. เพิ่มนิสิตเข้า section ใหม่

ถ้าข้อ 2 ล้มเหลว → นิสิตหลุดจากทุกกลุ่ม

สถานะการทำงานของทรานแซกชัน

ทรานแซกชันเริ่มที่ Active (กำลังรันคำสั่ง) แล้วจบด้วย COMMIT (ยืนยัน — การเปลี่ยนแปลงถาวร) หรือ ROLLBACK (ยกเลิก — ย้อนกลับทุกอย่างตั้งแต่เริ่มทรานแซกชัน)

9.2 คุณสมบัติ ACID

คุณสมบัติ ACID ของทรานแซกชัน
คุณสมบัติความหมายตัวอย่างในระบบลงทะเบียนDBMS รับประกันด้วย
Atomicityสำเร็จทั้งหมดหรือยกเลิกทั้งหมดเปิด section ใหม่ + ลงทะเบียนนิสิต ต้องสำเร็จพร้อมกันUndo Log / ROLLBACK
Consistencyฐานข้อมูลถูกต้องตามกฎทั้งก่อนและหลังเกรดต้องอยู่ใน A–F, FK ต้องอ้างอิงได้Constraint, Trigger
Isolationทรานแซกชันพร้อมกันไม่รบกวนกัน2 คนแย่งที่นั่งสุดท้าย ต้องได้คนเดียวLock, MVCC, Isolation Level
DurabilityCOMMIT แล้วต้องคงอยู่แม้ระบบล่มแจ้งว่าลงสำเร็จแล้ว ไฟดับข้อมูลต้องไม่หายRedo Log บนดิสก์

สถานการณ์ใดเกี่ยวกับคุณสมบัติใด
(ก) ไฟดับหลังระบบแจ้งว่าลงทะเบียนสำเร็จ เปิดเครื่องใหม่ข้อมูลยังอยู่
(ข) เพิ่ม section สำเร็จแต่ลงทะเบียนล้มเหลว ระบบยกเลิก section นั้นด้วย
(ค) ระบบไม่ยอมให้บันทึกเกรด E
(ง) อาจารย์ 2 คนแก้เกรดนิสิตคนเดียวกันพร้อมกัน ผลลัพธ์ไม่ปนกัน

(ก) Durability
(ข) Atomicity
(ค) Consistency
(ง) Isolation

9.3 autocommit และคำสั่งควบคุมทรานแซกชัน

MySQL ทำงานแบบ autocommit = 1 โดยปริยาย — ทุกคำสั่งเป็นทรานแซกชันของตัวเองและถูก COMMIT ทันทีที่รันเสร็จ

SELECT @@autocommit;
คำสั่งหน้าที่
START TRANSACTION (หรือ BEGIN)เริ่มทรานแซกชัน — ปิด autocommit ชั่วคราวจนกว่าจะ COMMIT/ROLLBACK
COMMITยืนยันการเปลี่ยนแปลงทั้งหมด
ROLLBACKยกเลิกการเปลี่ยนแปลงทั้งหมดตั้งแต่ START TRANSACTION
SAVEPOINT ชื่อทำจุดบันทึกย่อย
ROLLBACK TO SAVEPOINT ชื่อย้อนกลับถึงจุดบันทึก (ทรานแซกชันยังไม่จบ)
SET autocommit = 0ปิด autocommit ทั้ง session — ทุกคำสั่งรอ COMMIT
⚠️ DBeaver

DBeaver มีปุ่ม Auto / Manual commit บนแถบเครื่องมือ — ถ้าตั้งเป็น Manual ต้องกด Commit เอง มิฉะนั้นการแก้ไขจะหายเมื่อปิด connection และผู้ใช้อื่นจะไม่เห็นข้อมูลที่แก้

ROLLBACK — ย้อนกลับทั้งหมด

START TRANSACTION; DELETE FROM enroll; SELECT COUNT(*) AS rows_in_enroll FROM enroll; ROLLBACK; SELECT COUNT(*) AS rows_in_enroll FROM enroll;

COMMIT — ยืนยัน

START TRANSACTION; INSERT INTO section (subid, lecid, term) VALUES ('CS010', 't14', '2026-1'); INSERT INTO enroll (secid, stdid, grade) VALUES (LAST_INSERT_ID(), '60004', NULL); COMMIT; SELECT sec.secid, sec.subid, sec.term, e.stdid FROM section sec LEFT JOIN enroll e ON sec.secid = e.secid WHERE sec.term = '2026-1';

หลัง COMMIT สั่ง ROLLBACK ก็ย้อนกลับไม่ได้แล้ว

ROLLBACK; SELECT COUNT(*) AS n_section_2026_1 FROM section WHERE term = '2026-1';

นิสิต 60008 ลงทะเบียน section 51 (CS004, 2026-1) อยู่ จงเขียนทรานแซกชันย้ายไป section ใหม่ที่เพิ่งเปิดในหัวข้อนี้ (CS010, 2026-1) โดยทั้งการลบและการเพิ่มต้องสำเร็จพร้อมกัน

START TRANSACTION; DELETE FROM enroll WHERE secid = 51 AND stdid = '60008'; INSERT INTO enroll (secid, stdid) SELECT secid, '60008' FROM section WHERE subid = 'CS010' AND term = '2026-1'; COMMIT; SELECT e.secid, s.subid, s.term, e.stdid FROM enroll e JOIN section s ON e.secid = s.secid WHERE e.stdid = '60008' AND s.term = '2026-1';

9.4 SAVEPOINT — ย้อนกลับบางส่วน

START TRANSACTION; UPDATE lecturer SET salary = salary + 1000 WHERE major = 'CS'; SAVEPOINT after_cs; UPDATE lecturer SET salary = salary + 5000 WHERE major = 'DC'; ROLLBACK TO SAVEPOINT after_cs; -- ยกเลิกเฉพาะของสาขา DC COMMIT; -- ยืนยันเฉพาะของสาขา CS SELECT lecid, name, salary, major FROM lecturer WHERE major IN ('CS', 'DC');

ใช้ SAVEPOINT เมื่อทรานแซกชันยาวและมีบางขั้นตอนที่ “ผิดพลาดได้แต่ไม่ร้ายแรง” — เช่น ลงทะเบียนหลายวิชา วิชาไหนเต็มก็ข้ามไป แต่วิชาที่ลงได้ยังคงอยู่

START TRANSACTION; INSERT INTO enroll (secid, stdid) VALUES (52, '60015'); -- วิชาที่ 1 SAVEPOINT s1; INSERT INTO enroll (secid, stdid) VALUES (44, '60015'); -- วิชาที่ 2 ROLLBACK TO SAVEPOINT s1; -- ยกเลิกวิชาที่ 2 INSERT INTO enroll (secid, stdid) VALUES (47, '60015'); -- วิชาที่ 3 COMMIT; SELECT * FROM enroll WHERE stdid = '60015';

9.5 Implicit Commit — คำสั่งที่ย้อนกลับไม่ได้

คำสั่ง DDL (CREATE, ALTER, DROP, TRUNCATE, RENAME) และคำสั่งจัดการผู้ใช้ (CREATE USER, GRANT) จะ COMMIT ทรานแซกชันที่ค้างอยู่โดยอัตโนมัติ ก่อนทำงาน

START TRANSACTION; DELETE FROM enroll WHERE grade = 'F'; CREATE TABLE tmp_note (id INT); -- Implicit Commit เกิดขึ้นตรงนี้! ROLLBACK; SELECT COUNT(*) AS n_F_left FROM enroll WHERE grade = 'F';
⚠️ ผลที่ได้

การลบเกรด F ถูกยืนยันไปแล้ว ROLLBACK ไม่มีผล — แยกคำสั่ง DDL ออกจากทรานแซกชันที่จัดการข้อมูลเสมอ

SELECT 1;

9.6 ทรานแซกชันกับข้อผิดพลาด

ถ้าคำสั่งหนึ่งในทรานแซกชันเกิด error MySQL ไม่ได้ ROLLBACK ให้อัตโนมัติ — คำสั่งก่อนหน้ายังค้างอยู่ในทรานแซกชัน ผู้เขียนโปรแกรมต้องตัดสินใจเองว่าจะ COMMIT หรือ ROLLBACK

START TRANSACTION; INSERT INTO section (subid, lecid, term) VALUES ('MA003', 't15', '2026-1'); SELECT * FROM section WHERE term = '2026-1'; INSERT INTO enroll (secid, stdid) VALUES (LAST_INSERT_ID(), '99999'); ROLLBACK; SELECT * FROM section WHERE term = '2026-1';
✅ ในโปรแกรมจริง

เขียนเป็น try / except — ทุกคำสั่งสำเร็จ → commit(), มี error → rollback() หรือเขียนใน Stored Procedure ที่มี DECLARE EXIT HANDLER FOR SQLEXCEPTION (บทที่ 11)

Python (mysql-connector)
try:
    cur.execute("INSERT INTO section (subid, lecid, term) VALUES (%s, %s, %s)", ("MA003", "t15", "2026-1"))
    secid = cur.lastrowid
    cur.execute("INSERT INTO enroll (secid, stdid) VALUES (%s, %s)", (secid, "60014"))
    conn.commit()          # สำเร็จทั้งหมด
except Exception as e:
    conn.rollback()        # ล้มเหลวขั้นใดขั้นหนึ่ง → ยกเลิกทั้งหมด
    print("ลงทะเบียนไม่สำเร็จ:", e)

จงเขียนทรานแซกชันที่ (1) เปิดกลุ่มเรียนวิชา MA003 อาจารย์ t15 ภาค 2026-1 (2) ลงทะเบียนนิสิต 60014 และ 60015 ในกลุ่มนั้น — ใช้ตัวแปร @new_sec เก็บรหัสกลุ่มใหม่

START TRANSACTION; INSERT INTO section (subid, lecid, term) VALUES ('MA003', 't15', '2026-1'); SET @new_sec = LAST_INSERT_ID(); INSERT INTO enroll (secid, stdid) VALUES (@new_sec, '60014'), (@new_sec, '60015'); COMMIT; SELECT * FROM enroll WHERE secid = @new_sec;

ต้องเก็บ LAST_INSERT_ID() ไว้ในตัวแปรก่อน เพราะถ้ามี INSERT ตาราง AUTO_INCREMENT อื่นคั่น ค่าจะเปลี่ยน

9.7 ปัญหาจากการทำงานพร้อมกัน

เมื่อผู้ใช้หลายคน (หลาย session) อ่านเขียนข้อมูลชุดเดียวกันพร้อมกัน อาจเกิดปัญหา 4 แบบ — ตารางด้านล่างแสดงลำดับเวลาของ 2 session (A และ B)

Lost Update — การแก้ไขหาย

เวลาSession A (อาจารย์ฝ่ายวิชาการ)Session B (ฝ่ายบุคคล)
t1อ่าน salary ของ t01 = 40000
t2อ่าน salary ของ t01 = 40000
t3เขียน 40000 + 5000 = 45000
t4เขียน 40000 × 1.10 = 44000 → การเพิ่ม 5000 ของ A หายไป

Dirty Read — อ่านข้อมูลที่ยังไม่ยืนยัน

เวลาSession ASession B
t1START TRANSACTION; UPDATE enroll SET grade='D' (จาก F)
t2อ่านรายงานนิสิตที่ติด F → ไม่พบนิสิตคนนี้
t3ROLLBACK (เกรดกลับเป็น F)รายงานที่ออกไปผิด

Non-repeatable Read — อ่านซ้ำได้ค่าต่างกัน

เวลาSession ASession B
t1อ่าน gpa ของ 60001 = 3.75
t2UPDATE gpa = 3.80; COMMIT
t3อ่านอีกครั้ง = 3.80 (ในทรานแซกชันเดียวกัน)

Phantom Read — เจอแถวผี

เวลาSession ASession B
t1นับนิสิตใน section 51 = 2 คน
t2INSERT นิสิตใหม่เข้า section 51; COMMIT
t3นับอีกครั้ง = 3 คน (มีแถวใหม่โผล่มา)

9.8 ระดับการแยกรายการ (Isolation Level)

DBMS ให้เลือกระดับความเข้มงวด — ยิ่งเข้มงวดยิ่งถูกต้อง แต่ทำงานพร้อมกันได้น้อยลง (ช้าลง)

Isolation LevelDirty ReadNon-repeatable ReadPhantom Read
READ UNCOMMITTEDเกิดได้เกิดได้เกิดได้
READ COMMITTEDป้องกันเกิดได้เกิดได้
REPEATABLE READ (ค่าปริยาย MySQL)ป้องกันป้องกันป้องกันเกือบทั้งหมด
SERIALIZABLEป้องกันป้องกันป้องกัน
SELECT @@transaction_isolation; SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED; SELECT @@transaction_isolation; SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
📝 ทดลองเองด้วย 2 หน้าต่าง

ใน DBeaver เปิด SQL Editor 2 แท็บ (แต่ละแท็บเป็นคนละ session เมื่อเปิด “Open separate connection for each editor”) แล้วทำตามตารางเวลาในหัวข้อ 9.7 — สลับรันทีละบรรทัดเพื่อดูว่าแต่ละระดับเห็นข้อมูลต่างกันอย่างไร

9.9 การล็อก (Locking) และ Deadlock

REPEATABLE READ ป้องกันการ “อ่าน” ที่ผิดปกติ แต่ไม่ป้องกัน Lost Update ที่เกิดจาก “อ่านแล้วค่อยเขียน” — แก้ด้วย SELECT … FOR UPDATE ซึ่งล็อกแถวที่อ่านไว้ จน session อื่นที่จะแก้แถวเดียวกันต้องรอ

START TRANSACTION; SELECT lecid, salary FROM lecturer WHERE lecid = 't01' FOR UPDATE; -- ล็อกแถว t01 UPDATE lecturer SET salary = salary + 5000 WHERE lecid = 't01'; COMMIT; -- ปลดล็อก SELECT lecid, salary FROM lecturer WHERE lecid = 't01';
เวลาSession ASession B
t1SELECT … WHERE lecid='t01' FOR UPDATE (ล็อก)
t2SELECT … WHERE lecid='t01' FOR UPDATE → รอ
t3UPDATE +5000; COMMIT (ปลดล็อก)
t4ได้ค่าล่าสุด 45000 แล้วจึง ×1.10 → ไม่มีการแก้ไขหาย

Deadlock

เกิดเมื่อ 2 ทรานแซกชันต่างรอล็อกที่อีกฝ่ายถืออยู่ — MySQL ตรวจพบและยกเลิกฝ่ายหนึ่งอัตโนมัติ (Error 1213 Deadlock found) ฝ่ายที่ถูกยกเลิกต้องลองใหม่

เวลาSession ASession B
t1UPDATE lecturer … WHERE lecid='t01' (ล็อก t01)
t2UPDATE lecturer … WHERE lecid='t02' (ล็อก t02)
t3UPDATE … WHERE lecid='t02' → รอ B
t4UPDATE … WHERE lecid='t01' → รอ A → Deadlock! MySQL ยกเลิก B
✅ ลดโอกาส Deadlock
  • เข้าถึงแถว/ตารางในลำดับเดียวกันทุกทรานแซกชัน (เช่น เรียงตาม lecid เสมอ)
  • ทำทรานแซกชันให้สั้น — ไม่รอ input จากผู้ใช้กลางทรานแซกชัน
  • มีดัชนีที่เหมาะสม เพื่อล็อกเฉพาะแถวที่จำเป็น
  • เตรียมโค้ดให้ลองใหม่ (retry) เมื่อเจอ Error 1213

ระบบลงทะเบียน: นิสิตกดลงทะเบียน → ระบบนับจำนวนคนในกลุ่ม → ถ้าน้อยกว่า 40 จึง INSERT — ถ้านิสิต 2 คนกดพร้อมกันตอนมี 39 คน จะเกิดอะไรขึ้น และควรแก้อย่างไร

ทั้งสองคนนับได้ 39 พร้อมกัน → ทั้งคู่ INSERT สำเร็จ → กลุ่มมี 41 คน (คล้าย Lost Update / Phantom)

แก้โดยทำทั้งหมดในทรานแซกชันเดียว และล็อกข้อมูลที่ใช้ตัดสินใจ เช่น SELECT … FROM section WHERE secid = ? FOR UPDATE ก่อนนับ (session ที่สองต้องรอ) หรือใช้ระดับ SERIALIZABLE เฉพาะทรานแซกชันนี้ หรือบังคับด้วย Trigger (บทที่ 12)
  • แนวคิดและ ACID
  • จงอธิบายความหมายของทรานแซกชัน และยกตัวอย่างงานในระบบลงทะเบียนที่ต้องทำเป็นทรานแซกชัน (ทั้งหมดหรือไม่มีเลย)

    ทรานแซกชัน คือหน่วยของงานที่ประกอบด้วยคำสั่งหนึ่งหรือหลายคำสั่ง ซึ่งต้องสำเร็จทั้งหมด หรือไม่เกิดผลเลย และทำให้ฐานข้อมูลเปลี่ยนจากสถานะที่ถูกต้องหนึ่งไปยังอีกสถานะที่ถูกต้อง

    • ย้ายกลุ่มเรียน (ลบจากกลุ่มเดิม + เพิ่มในกลุ่มใหม่)
    • เปิดกลุ่มเรียนใหม่พร้อมลงทะเบียนนิสิตชุดแรก
    • ชำระค่าลงทะเบียน (บันทึกการชำระ + เปลี่ยนสถานะการลงทะเบียน)
    • ลงทะเบียนที่นั่งสุดท้าย (ตรวจจำนวนคงเหลือ + เพิ่มการลงทะเบียน)
  • จงจับคู่สถานการณ์กับคุณสมบัติ ACID: ไฟดับหลังแจ้งว่าลงทะเบียนสำเร็จ · 2 คนแย่งที่นั่งสุดท้าย · เปิด section สำเร็จแต่ลงทะเบียนล้มเหลว · ที่นั่งคงเหลือติดลบ (A C I D)

    ไฟดับหลังแจ้งว่าสำเร็จ (ข้อมูลต้องยังอยู่) = Durability · 2 คนแย่งที่นั่งสุดท้าย = Isolation · เปิด section สำเร็จแต่ลงทะเบียนล้มเหลว (ต้องยกเลิกทั้งชุด) = Atomicity · ที่นั่งคงเหลือติดลบ (ผิดกฎ) = Consistency

  • คำสั่งควบคุมทรานแซกชัน
  • จงเขียนทรานแซกชันเปิดกลุ่มเรียนใหม่ และลงทะเบียนนิสิต 2 คนในกลุ่มนั้น หากขั้นตอนใดล้มเหลวให้ยกเลิกทั้งหมด (START TRANSACTION … COMMIT / ROLLBACK)

    ใช้ LAST_INSERT_ID() รับ secid ที่เพิ่งสร้าง ถ้าคำสั่งใดเกิด error ให้สั่ง ROLLBACK แทน COMMIT (ในโปรแกรมจริงตรวจ error ทุกขั้น หรือเขียนเป็นโพรซีเยอร์ที่มี EXIT HANDLER — บทที่ 11)

    START TRANSACTION; INSERT INTO section (subid, lecid, term) VALUES ('CS010', 't01', '2026-2'); SET @new_sec = LAST_INSERT_ID(); INSERT INTO enroll (secid, stdid) VALUES (@new_sec, '60001'), (@new_sec, '60004'); COMMIT;

    ถ้าเปลี่ยนรหัสนิสิตคนที่สองเป็นรหัสที่ไม่มีอยู่ INSERT enroll จะเกิด Error 1452 — สั่ง ROLLBACK แล้วกลุ่มเรียนใหม่ก็จะถูกยกเลิกไปด้วย

    START TRANSACTION; UPDATE lecturer SET salary = salary * 1.10 WHERE major = 'CS'; SAVEPOINT after_cs; UPDATE lecturer SET salary = salary * 1.10 WHERE major = 'DC'; ROLLBACK TO SAVEPOINT after_cs; -- ยกเลิกเฉพาะของ DC COMMIT; -- ยืนยันของ CS

    START TRANSACTION; INSERT INTO enroll (secid, stdid, grade) SELECT 21, stdid, grade FROM enroll WHERE secid = 20 AND stdid = '60009'; DELETE FROM enroll WHERE secid = 20 AND stdid = '60009'; SELECT * FROM enroll WHERE stdid = '60009' AND secid IN (20, 21); -- ตรวจก่อนCOMMIT; -- ถ้าผลถูกต้อง (ถ้าผิดให้ ROLLBACK)
  • autocommit คืออะไร ถ้าปิด autocommit แล้วลืม COMMIT จะเกิดอะไรขึ้นเมื่อปิดการเชื่อมต่อ (ROLLBACK อัตโนมัติ)

    autocommit (ค่าปริยาย = 1) ทำให้ทุกคำสั่งเป็นทรานแซกชันของตัวเองและ COMMIT ทันทีที่ทำเสร็จ ถ้าปิด (SET autocommit = 0) คำสั่งจะสะสมอยู่ในทรานแซกชันจนกว่าจะ COMMIT — ถ้าปิดการเชื่อมต่อโดยไม่ COMMIT MySQL จะ ROLLBACK ทุกอย่างที่ยังไม่ยืนยัน และระหว่างนั้นแถวที่แก้ยังถูกล็อกไว้ ผู้ใช้อื่นอาจต้องรอ

    SELECT @@autocommit;
  • เหตุใดไม่ควรใส่คำสั่ง CREATE / ALTER / DROP ไว้กลางทรานแซกชันใน MySQL (Implicit Commit)

    คำสั่ง DDL ทำให้เกิด Implicit Commit — MySQL จะ COMMIT ทุกอย่างที่ทำมาก่อนหน้าในทรานแซกชันโดยอัตโนมัติ ROLLBACK หลังจากนั้นจึงย้อนกลับไม่ได้ และตัว DDL เองก็ย้อนกลับไม่ได้

    START TRANSACTION; UPDATE lecturer SET salary = 99999 WHERE lecid = 't02'; CREATE TABLE tmp_x (id INT); -- Implicit Commit ROLLBACK; -- สายไปแล้ว SELECT lecid, salary FROM lecturer WHERE lecid = 't02';

  • จงยกตัวอย่าง Lost Update, Dirty Read, Non-repeatable Read และ Phantom Read ในระบบลงทะเบียน และระบุระดับการแยกรายการที่ป้องกันได้ (หัวข้อ 9.7–9.8)
    • Lost Update — เจ้าหน้าที่ 2 คนอ่านจำนวนที่นั่งคงเหลือ = 1 พร้อมกัน ต่างคนลบ 1 แล้วบันทึก ค่าสุดท้ายเป็น 0 ทั้งที่ลงไป 2 คน → ป้องกันด้วยการล็อก (SELECT … FOR UPDATE) ทุกระดับ
    • Dirty Read — อาจารย์ A แก้เกรดยังไม่ COMMIT นิสิตเปิดดูเห็นเกรดใหม่ แล้ว A สั่ง ROLLBACK → ป้องกันได้ตั้งแต่ READ COMMITTED
    • Non-repeatable Read — รายงานอ่านเกรดของนิสิตคนหนึ่ง 2 ครั้งในทรานแซกชันเดียว แต่ระหว่างนั้นมีคนแก้เกรดและ COMMIT ทำให้ได้ค่าต่างกัน → ป้องกันได้ตั้งแต่ REPEATABLE READ
    • Phantom Read — นับนิสิตในกลุ่มเรียนได้ 39 คน ระหว่างนั้นมีคนลงเพิ่มและ COMMIT นับใหม่ได้ 40 → มาตรฐานป้องกันที่ SERIALIZABLE (InnoDB ใน REPEATABLE READ ป้องกันการอ่านแบบ consistent read ได้ด้วย snapshot แต่การอ่านแบบล็อกยังต้องระวัง)
  • ระดับการแยกรายการใดเหมาะกับระบบลงทะเบียนเรียนที่สุด เพราะเหตุใด (ความถูกต้อง vs ประสิทธิภาพ)

    ใช้ REPEATABLE READ (ค่าปริยายของ MySQL) เป็นพื้นฐาน เพราะป้องกัน Dirty Read และ Non-repeatable Read ได้โดยยังรองรับผู้ใช้พร้อมกันจำนวนมากในช่วงลงทะเบียน แล้วใช้ SELECT … FOR UPDATE เฉพาะจุดวิกฤต (ตรวจที่นั่งคงเหลือ) แทนการใช้ SERIALIZABLE ทั้งระบบซึ่งปลอดภัยที่สุดแต่ทำให้ต้องรอกันมากและเกิด deadlock บ่อย

  • อธิบายการใช้ SELECT … FOR UPDATE ป้องกันการแย่งที่นั่งสุดท้าย (ล็อกแถว)

    ภายในทรานแซกชัน SELECT … FOR UPDATE อ่านพร้อมล็อกแถวที่อ่าน ผู้ใช้คนที่สองที่สั่ง FOR UPDATE แถวเดียวกันต้องรอจนคนแรก COMMIT หรือ ROLLBACK แล้วจึงอ่านค่าล่าสุด (ที่นั่งเหลือ 0) จึงไม่ลงทะเบียนเกินจำนวน

    START TRANSACTION; SELECT seats_left FROM section WHERE secid = 52 FOR UPDATE; -- ล็อกแถว (คนที่ 2 ต้องรอตรงนี้) -- ถ้า seats_left > 0 INSERT INTO enroll (secid, stdid) VALUES (52, '60015'); UPDATE section SET seats_left = seats_left - 1 WHERE secid = 52; COMMIT; -- ปลดล็อก
  • Deadlock เกิดขึ้นได้อย่างไร และ DBMS จัดการอย่างไร (ทรานแซกชันหนึ่งถูก ROLLBACK)

    Deadlock เกิดเมื่อทรานแซกชันสองตัวต่างถือล็อกที่อีกฝ่ายต้องการ และรอกันเป็นวง เช่น T1 ล็อก t01 แล้วขอ t02 ขณะที่ T2 ล็อก t02 แล้วขอ t01 — ไม่มีใครไปต่อได้

    InnoDB ตรวจพบวงรอนี้อัตโนมัติ แล้วเลือกทรานแซกชันหนึ่ง (ตัวที่แก้ข้อมูลน้อยกว่า) เป็น “เหยื่อ” สั่ง ROLLBACK และคืน Error 1213 อีกตัวจึงทำงานต่อได้ — โปรแกรมควรดัก error นี้แล้วลองทำทรานแซกชันใหม่ และลดโอกาสเกิดโดยล็อกแถวตามลำดับเดียวกันเสมอ ทำทรานแซกชันให้สั้น
