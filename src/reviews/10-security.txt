## ผู้ใช้และสิทธิ์
สร้างบัญชี advisor ที่เชื่อมต่อได้จากเครื่องเดียวกันเท่านั้น ให้สิทธิ์อ่าน student และ enroll และแก้ไขได้เฉพาะคอลัมน์ grade || GRANT UPDATE (grade)
```
CREATE USER 'advisor'@'localhost' IDENTIFIED BY 'Adv#2026';

GRANT SELECT ON std_66011200.student TO 'advisor'@'localhost';
GRANT SELECT, UPDATE (grade) ON std_66011200.enroll TO 'advisor'@'localhost';

SHOW GRANTS FOR 'advisor'@'localhost';
```
A: <code>@'localhost'</code> จำกัดให้เชื่อมต่อได้จากเครื่องเซิร์ฟเวอร์เท่านั้น และ <code>UPDATE (grade)</code> อนุญาตให้แก้เฉพาะคอลัมน์ grade — ถ้าสั่ง <code>UPDATE enroll SET stdid = …</code> จะถูกปฏิเสธ
ยกเลิกสิทธิ์แก้ไขทั้งหมดของบัญชี advisor แล้วตรวจสอบผล || REVOKE / SHOW GRANTS
```
REVOKE UPDATE (grade) ON std_66011200.enroll FROM 'advisor'@'localhost';
SHOW GRANTS FOR 'advisor'@'localhost';   -- เหลือเพียง SELECT บน student และ enroll
```
`'teacher'@'localhost'` กับ `'teacher'@'%'` ต่างกันอย่างไร ควรใช้แบบใดในระบบจริง || host
A: บัญชีใน MySQL ระบุด้วย <b>ชื่อผู้ใช้ + host</b> สองบัญชีนี้จึงเป็นคนละบัญชี — <code>'teacher'@'localhost'</code> เชื่อมต่อได้จากเครื่องเซิร์ฟเวอร์เท่านั้น ส่วน <code>'teacher'@'%'</code> เชื่อมต่อได้จาก<b>ทุกเครื่อง</b>
A: ระบบจริงควรจำกัด host ให้แคบที่สุดเท่าที่ใช้งานได้ เช่น <code>'teacher'@'192.168.1.%'</code> (เฉพาะเครือข่ายภายใน) หรือ localhost สำหรับบัญชีที่ใช้โดยเว็บแอปบนเครื่องเดียวกัน หลีกเลี่ยง '%' โดยเฉพาะกับบัญชีที่มีสิทธิ์สูง
จงอธิบายหลักการให้สิทธิ์เท่าที่จำเป็น และออกแบบสิทธิ์ของนิสิต อาจารย์ เจ้าหน้าที่ทะเบียน และผู้ดูแลระบบ || Least Privilege
A: <b>Principle of Least Privilege</b> — ผู้ใช้แต่ละคนได้รับสิทธิ์เพียงเท่าที่จำเป็นต่อการทำงานเท่านั้น ถ้าบัญชีถูกขโมยหรือใช้ผิดพลาด ความเสียหายจะจำกัด
A- <b>นิสิต</b> — SELECT ผ่านวิวที่แสดงเฉพาะข้อมูลของตนเอง (ทรานสคริปต์) และรายวิชาที่เปิด
A- <b>อาจารย์</b> — SELECT รายชื่อในกลุ่มที่สอน (ผ่านวิว) + UPDATE (grade) ของ enroll
A- <b>เจ้าหน้าที่ทะเบียน</b> — SELECT, INSERT, UPDATE บน student, section, enroll (ไม่ให้ DELETE หรือ DROP)
A- <b>ผู้ดูแลระบบ (DBA)</b> — ALL PRIVILEGES รวมการสร้างผู้ใช้และสำรองข้อมูล (บัญชีแยก ใช้เท่าที่จำเป็น)
เหตุใดจึงไม่ควรใช้ WITH GRANT OPTION กับผู้ใช้ทั่วไป || สิทธิ์แพร่กระจาย
A: <code>WITH GRANT OPTION</code> ทำให้ผู้รับสิทธิ์<b>ส่งต่อสิทธิ์</b>นั้นให้ผู้อื่นได้ สิทธิ์จะแพร่กระจายออกไปโดย DBA ควบคุมและตรวจสอบไม่ได้ว่าใครมีสิทธิ์อะไร จึงควรให้เฉพาะผู้ดูแลระบบ
## Role และวิว
ออกแบบ Role สำหรับระบบห้องสมุดที่มีสมาชิก บรรณารักษ์ และผู้ดูแลระบบ พร้อมเขียนคำสั่ง || CREATE ROLE / GRANT role TO user
```
CREATE ROLE 'role_member', 'role_librarian', 'role_admin';

GRANT SELECT ON library.book     TO 'role_member';
GRANT SELECT ON library.category TO 'role_member';

GRANT SELECT, INSERT, UPDATE ON library.*      TO 'role_librarian';
GRANT DELETE                 ON library.borrow TO 'role_librarian';

GRANT ALL PRIVILEGES ON library.* TO 'role_admin';

CREATE USER 'somchai'@'localhost' IDENTIFIED BY 'Lib#2026';
GRANT 'role_librarian' TO 'somchai'@'localhost';
SET DEFAULT ROLE 'role_librarian' TO 'somchai'@'localhost';
```
A: ข้อดีของ Role: กำหนดสิทธิ์เป็นกลุ่มครั้งเดียว เมื่อมีบรรณารักษ์ใหม่ก็ GRANT role ให้ทันที และเปลี่ยนสิทธิ์ของทั้งกลุ่มได้ที่จุดเดียว
สร้างวิวที่แสดงเฉพาะรหัส ชื่อ สาขาของนิสิต แล้วให้สิทธิ์ผู้ใช้ guest อ่านเฉพาะวิวนี้ อธิบายประโยชน์ || GRANT SELECT ON view
```exec
CREATE OR REPLACE VIEW v_student_public AS
    SELECT    stdid, name, major
    FROM      student;
```
```
CREATE USER 'guest'@'localhost' IDENTIFIED BY 'Guest#2026';
GRANT SELECT ON std_66011200.v_student_public TO 'guest'@'localhost';
```
A: guest เห็นเพียงรหัส ชื่อ สาขา ไม่เห็น gpa และวันเกิด และไม่มีสิทธิ์บนตาราง student โดยตรง — เป็นการควบคุมสิทธิ์<b>ระดับคอลัมน์และแถว</b>ด้วยวิว (บทที่ 7) ถ้าภายหลังต้องซ่อนข้อมูลเพิ่ม แก้วิวที่เดียว
## SQL Injection และแนวปฏิบัติ
อธิบายการแทรกคำสั่ง SQL พร้อมยกตัวอย่างคำสั่งที่มีช่องโหว่ และเขียนคำสั่งที่แก้ให้ปลอดภัย || Prepared Statement
A: <b>SQL Injection</b> เกิดเมื่อโปรแกรมนำข้อความที่ผู้ใช้ป้อน<b>ต่อสตริง</b>เข้าไปในคำสั่ง SQL ผู้โจมตีจึงป้อนข้อความที่เป็นส่วนของคำสั่ง SQL เพื่อเปลี่ยนความหมายของคำสั่งได้
```
# มีช่องโหว่ (Python) — ผู้ใช้ป้อน  ' OR '1'='1
sql = "SELECT * FROM student WHERE stdid = '" + user_input + "'"
# ได้คำสั่ง: SELECT * FROM student WHERE stdid = '' OR '1'='1'  → คืนนิสิตทุกคน

# ปลอดภัย — Prepared Statement / Parameterized Query
cursor.execute("SELECT * FROM student WHERE stdid = %s", (user_input,))
```
```run title="Prepared Statement ใน MySQL — ค่าที่ป้อนถูกมองเป็นข้อมูลล้วน ไม่ใช่คำสั่ง"
PREPARE stmt FROM 'SELECT stdid, name FROM student WHERE stdid = ?';
SET @input = ''' OR ''1''=''1';
EXECUTE stmt USING @input;
```
ผู้โจมตีป้อน username `admin' -- ` ในหน้าเข้าสู่ระบบที่ต่อสตริง SQL จะเกิดอะไรขึ้น || -- คือคอมเมนต์
A: คำสั่งที่ได้คือ <code>SELECT * FROM users WHERE username = 'admin' -- ' AND password = '…'</code> — <code>--</code> (ตามด้วยช่องว่าง) ทำให้ส่วนที่เหลือกลายเป็นคอมเมนต์ <b>เงื่อนไขรหัสผ่านถูกตัดทิ้ง</b> ผู้โจมตีจึงเข้าสู่ระบบเป็น admin ได้โดยไม่ต้องรู้รหัสผ่าน แก้ด้วย Prepared Statement
เหตุใดจึงห้ามเก็บรหัสผ่านเป็นข้อความธรรมดา และควรเก็บอย่างไร || bcrypt / Argon2 + salt
A: ถ้าฐานข้อมูลรั่วไหล ผู้โจมตีได้รหัสผ่านของทุกคนทันที และผู้ใช้มักใช้รหัสเดียวกันหลายระบบ ผู้ดูแลระบบเองก็ไม่ควรเห็นรหัสผ่าน
A: ควรเก็บเป็น <b>ค่าแฮชทางเดียวแบบช้าที่มี salt</b> เช่น bcrypt, scrypt หรือ Argon2 (salt สุ่มต่างกันทุกบัญชี ป้องกัน rainbow table) ตอนเข้าสู่ระบบให้แฮชรหัสที่ป้อนแล้วเทียบ — ไม่ใช้ MD5/SHA-1 ธรรมดาเพราะเร็วเกินไป ถูกเดาได้ง่าย
เขียนคำสั่งสำรองฐานข้อมูลด้วย mysqldump และกู้คืน แล้วอธิบายว่าทำไมต้องทดสอบการกู้คืนเป็นระยะ || mysqldump > / mysql <
```
# สำรอง (รันใน Command Prompt / Terminal ไม่ใช่ใน DBeaver)
mysqldump -u root -p std_66011200 > backup_2026-10-02.sql

# กู้คืน
mysql -u root -p std_66011200 < backup_2026-10-02.sql
```
A: การสำรองที่ไม่เคยทดสอบกู้คืนอาจใช้ไม่ได้จริงเมื่อถึงเวลา (ไฟล์เสีย สำรองไม่ครบทุกตาราง สิทธิ์/เวอร์ชันไม่ตรง หรือไม่รู้ว่ากู้คืนใช้เวลานานเท่าไร) จึงต้องลองกู้คืนบนเครื่องทดสอบเป็นระยะ และเก็บไฟล์สำรองไว้นอกเครื่องเซิร์ฟเวอร์
ระบุมาตรการด้านความปลอดภัยที่ควรใช้กับระบบลงทะเบียนเรียนของมหาวิทยาลัยอย่างน้อย 5 ข้อ พร้อมเหตุผล || หัวข้อ 10.6
A- <b>Least Privilege + Role</b> — นิสิต อาจารย์ เจ้าหน้าที่ได้สิทธิ์ตามหน้าที่ ลดความเสียหายเมื่อบัญชีถูกขโมย
A- <b>Prepared Statement ทุกจุด</b> — ป้องกัน SQL Injection จากหน้าเว็บ
A- <b>แฮชรหัสผ่านด้วย bcrypt/Argon2</b> และบังคับรหัสผ่านที่แข็งแรง/ยืนยันตัวตนสองชั้น
A- <b>เข้ารหัสการเชื่อมต่อ (TLS/HTTPS)</b> และจำกัด host ที่เชื่อมต่อฐานข้อมูลได้ — ป้องกันการดักข้อมูล
A- <b>สำรองข้อมูลอัตโนมัติและทดสอบกู้คืน</b> — รับมือความเสียหาย/ransomware
A- <b>บันทึกและตรวจสอบ (Audit Log)</b> เช่น ทริกเกอร์บันทึกการแก้เกรด — ตรวจย้อนหลังได้ว่าใครแก้อะไร
A- <b>อัปเดตแพตช์</b> DBMS และระบบปฏิบัติการสม่ำเสมอ
