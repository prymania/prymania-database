## คีย์และกฎความคงสภาพ
จงอธิบายความแตกต่างระหว่าง Super Key, Candidate Key, Primary Key และ Alternate Key พร้อมตัวอย่างจากตาราง student || ตัดคอลัมน์ออกได้อีกไหม
A- <b>Super Key</b> — กลุ่มคอลัมน์ใดก็ได้ที่ระบุแถวได้ไม่ซ้ำ เช่น (stdid), (stdid, name), (stdid, major, gpa)
A- <b>Candidate Key</b> — Super Key ที่เล็กที่สุด ตัดคอลัมน์ใดออกแล้วจะไม่เป็นคีย์ เช่น (stdid) ถ้ามีเลขบัตรประชาชน (citizen_id) ก็เป็น Candidate Key อีกตัว
A- <b>Primary Key</b> — Candidate Key ที่เลือกมาใช้หลัก คือ stdid
A- <b>Alternate Key</b> — Candidate Key ที่ไม่ได้ถูกเลือก เช่น citizen_id (ควรกำหนด UNIQUE)
A: หมายเหตุ: name ไม่ใช่ Candidate Key เพราะชื่อซ้ำได้ (ในข้อมูลมี Gon 2 คน)
ตาราง section มีกฎ `UNIQUE (subid, lecid, term)` จงระบุ Candidate Key ทั้งหมดของตารางนี้ || secid, (subid, lecid, term)
A: Candidate Key มี 2 ชุด คือ <b>secid</b> (เลือกเป็น PK) และ <b>(subid, lecid, term)</b> (Alternate Key ที่บังคับด้วย UNIQUE)
เหตุใดค่า PK จึงเป็น NULL ไม่ได้ แต่ FK เป็น NULL ได้ ยกตัวอย่างจากคอลัมน์ `subject.pre` || Entity vs Referential Integrity
A: <b>Entity Integrity</b> — PK ใช้ระบุตัวตนของแถว ถ้าเป็น NULL (ไม่ทราบค่า) จะระบุแถวไม่ได้ จึงห้าม NULL
A: <b>Referential Integrity</b> — FK ต้องมีค่าตรงกับ PK ที่มีอยู่ <b>หรือเป็น NULL</b> ซึ่งหมายถึง “ไม่มีความสัมพันธ์” เช่น <code>subject.pre</code> ของ CS001 Programming เป็น NULL เพราะไม่มีวิชาบังคับก่อน
```run
SELECT subid, name, pre FROM subject WHERE pre IS NULL;
```
จงอธิบายกฎความคงสภาพ 4 ประเภท และระบุว่าแต่ละประเภทบังคับใช้ด้วยคำสั่ง SQL ใด || PK / FK / CHECK / Trigger
A- <b>Entity Integrity</b> — PK ไม่ซ้ำและไม่เป็น NULL → <code>PRIMARY KEY</code>
A- <b>Referential Integrity</b> — FK ต้องอ้างถึงแถวที่มีอยู่จริง → <code>FOREIGN KEY … REFERENCES</code>
A- <b>Domain Integrity</b> — ค่าต้องอยู่ในขอบเขตที่กำหนด → ชนิดข้อมูล, <code>NOT NULL</code>, <code>CHECK</code>, <code>DEFAULT</code>
A- <b>Business Rule (User-defined)</b> — กฎเฉพาะขององค์กร เช่น ห้ามลงทะเบียนเกิน 40 คน → <code>CHECK</code> หรือ <code>TRIGGER</code> (บทที่ 12)
คำสั่ง `INSERT INTO enroll VALUES (99, '60001', 'A');` จะเกิดอะไรขึ้น ละเมิดกฎข้อใด || secid 99 ไม่มีอยู่
A: เกิด Error 1452 เพราะไม่มี section รหัส 99 ในตาราง section — ละเมิด <b>Referential Integrity</b> (FK enroll_fk_sec)
```error
INSERT INTO enroll VALUES (99, '60001', 'A');
```
เหตุใดการใช้อีเมลหรือเบอร์โทรเป็น Primary Key จึงไม่เหมาะสม || คงที่ เล็ก ไม่มีความหมายทางธุรกิจ
A: PK ที่ดีควร <b>ไม่เปลี่ยนแปลง</b> สั้น และไม่เป็น NULL — อีเมล/เบอร์โทรเปลี่ยนได้ (ต้องแก้ FK ทุกตารางที่อ้างถึง) บางคนไม่มีหรือมีหลายค่า ยาวทำให้ดัชนีใหญ่ และอาจถูกนำไปใช้ใหม่โดยคนอื่น จึงควรใช้รหัสที่สร้างขึ้นเอง แล้วกำหนดอีเมลเป็น UNIQUE แทน

A: <code>employee(<u>emp_id</u>, name, house_id, road, province, postcode)</code> · <code>employee_language(<u>emp_id</u>, <u>language</u>)</code>

A: <b>รวม 1 ตาราง</b>: <code>student(<u>stdid</u>, name, username UNIQUE, password_hash, assigned_date)</code> — ง่าย ไม่ต้อง JOIN เหมาะเมื่อทุกคนมีบัญชี

## FD และนอร์มัลไลเซชัน
จงยกตัวอย่าง Insertion, Modification และ Deletion Anomaly จากตาราง `R(stdid, stdname, subid, subname, credit, grade)` || PK = (stdid, subid)
A- <b>Insertion</b> — เพิ่มวิชาใหม่ที่ยังไม่มีคนลงไม่ได้ เพราะ stdid (ส่วนของ PK) จะเป็น NULL
A- <b>Modification</b> — เปลี่ยนชื่อวิชา Java ต้องแก้ทุกแถวที่มีคนลง ถ้าแก้ไม่ครบจะมีชื่อวิชาไม่ตรงกัน
A- <b>Deletion</b> — ลบการลงทะเบียนของนิสิตคนสุดท้ายที่เรียนวิชาหนึ่ง ข้อมูลวิชานั้น (ชื่อ หน่วยกิต) หายไปด้วย
จงอธิบายความแตกต่างของ Full, Partial และ Transitive Functional Dependency พร้อมตัวอย่าง || X → Y
A- <b>Full FD</b> — Y ขึ้นกับ X ทั้งชุด ตัดส่วนใดออกไม่ได้ เช่น (stdid, subid) → grade
A- <b>Partial FD</b> — Y ขึ้นกับเพียงบางส่วนของคีย์ผสม เช่น (stdid, subid) → stdname แต่จริง ๆ stdid → stdname ก็พอ
A- <b>Transitive FD</b> — X → Y และ Y → Z โดย Y ไม่ใช่คีย์ ทำให้ X → Z ทางอ้อม เช่น stdid → major และ major → major_head
กำหนด `ORDER_DETAIL(order_id, product_id, product_name, unit_price, qty, customer_id, customer_name, order_date)` จงระบุ FD ทั้งหมด || PK = (order_id, product_id)
A- (order_id, product_id) → qty — Full FD
A- product_id → product_name, unit_price — Partial FD
A- order_id → customer_id, order_date — Partial FD
A- customer_id → customer_name — Transitive (order_id → customer_id → customer_name)
A: หมายเหตุ: ถ้าราคาขายแต่ละครั้งต่างกันได้ ควรเก็บราคาขาย ณ วันสั่งไว้ที่ (order_id, product_id) ด้วย
จากข้อที่แล้ว จงทำนอร์มัลไลเซชันจนถึง 3NF แสดงโครงสร้างในแต่ละขั้น (1NF → 2NF → 3NF) || แยกตามตัวกำหนด
A: <b>1NF</b> — ตารางเดิมทุกช่องมีค่าเดียวอยู่แล้ว PK = (order_id, product_id)
A: <b>2NF</b> — กำจัด Partial FD: <code>order_line(<u>order_id</u>, <u>product_id</u>, qty)</code> · <code>product(<u>product_id</u>, product_name, unit_price)</code> · <code>orders(<u>order_id</u>, customer_id, customer_name, order_date)</code>
A: <b>3NF</b> — กำจัด Transitive FD ใน orders: <code>orders(<u>order_id</u>, customer_id FK, order_date)</code> · <code>customer(<u>customer_id</u>, customer_name)</code> — ได้ 4 ตาราง: customer, orders, product, order_line
ตาราง `student(stdid, name, major, major_name, major_head)` อยู่ในนอร์มัลฟอร์มใด และต้องแก้อย่างไรให้อยู่ใน 3NF || Transitive
A: อยู่ใน <b>2NF</b> (PK มีคอลัมน์เดียว จึงไม่มี Partial FD) แต่ไม่อยู่ใน 3NF เพราะมี Transitive FD: stdid → major → major_name, major_head
A: แก้โดยแยก: <code>student(<u>stdid</u>, name, major FK)</code> · <code>major(<u>major</u>, major_name, major_head)</code>
ตาราง `TEACHING(student, subject, lecturer)` ที่อาจารย์ 1 คนสอนเพียงวิชาเดียว อยู่ใน 3NF แต่ไม่อยู่ใน BCNF เพราะเหตุใด || lecturer → subject
A: มี FD: (student, subject) → lecturer และ <b>lecturer → subject</b> คีย์คือ (student, subject) หรือ (student, lecturer) — ทุกคอลัมน์เป็นส่วนของคีย์ จึงผ่าน 3NF แต่ BCNF กำหนดว่าตัวกำหนดทุกตัวต้องเป็น Super Key ซึ่ง lecturer ไม่ใช่ จึงไม่ผ่าน BCNF
A: แยกเป็น <code>lecturer_subject(<u>lecturer</u>, subject)</code> และ <code>student_lecturer(<u>student</u>, <u>lecturer</u>)</code>
คอลัมน์ `student.gpa` ในกรณีศึกษาเป็นการดีนอร์มัลไลซ์หรือไม่ เพราะเหตุใด และมีความเสี่ยงอะไร || คำนวณได้จาก enroll + subject
A: <b>เป็น</b> — gpa คำนวณได้จากเกรดใน enroll และหน่วยกิตใน subject การเก็บซ้ำไว้ทำให้อ่านเร็ว แต่เสี่ยงต่อ<b>ความไม่สอดคล้อง</b> เมื่อแก้เกรดแล้วลืมคำนวณ gpa ใหม่ — ในกรณีศึกษาค่าก็ไม่ตรงกันจริง (ดูบทที่ 7 วิว v_student_gpa)
```run max="6"
SELECT s.stdid, s.name, s.gpa AS stored_gpa,
       ROUND(SUM(sub.credit * CASE e.grade WHEN 'A' THEN 4 WHEN 'B' THEN 3 WHEN 'C' THEN 2
                                            WHEN 'D' THEN 1 ELSE 0 END) / SUM(sub.credit), 2) AS calc_gpa
FROM   student s
       JOIN enroll  e   ON s.stdid = e.stdid
       JOIN section sec ON e.secid = sec.secid
       JOIN subject sub ON sec.subid = sub.subid
WHERE  e.grade IS NOT NULL
GROUP  BY s.stdid, s.name, s.gpa
ORDER  BY s.stdid;
```
ระบบรายงานยอดขายเก็บ `total_amount` ไว้ในตารางคำสั่งซื้อ แทนการคำนวณใหม่ทุกครั้ง มีข้อดีข้อเสียอย่างไร ควรมีมาตรการใดรองรับ || Trigger
A: <b>ข้อดี</b> — รายงานเร็ว ไม่ต้อง SUM รายการทุกครั้ง และเก็บยอด ณ เวลาขายได้ <b>ข้อเสีย</b> — ข้อมูลซ้ำซ้อน เสี่ยงยอดไม่ตรงกับรายการเมื่อแก้รายการ
A: <b>มาตรการ</b> — ใช้ทริกเกอร์ปรับ total_amount อัตโนมัติเมื่อ INSERT/UPDATE/DELETE รายการ (บทที่ 12) ทำทุกอย่างในทรานแซกชัน และมีคำสั่งตรวจ/คำนวณยอดใหม่เป็นระยะ
